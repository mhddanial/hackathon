# Oracle history migrations

Current implementation context: [Oracle context](../docs/oracle/context/CURRENT_STATE.md).
Applied legacy access repair: [RLS record](../docs/oracle/security/LEGACY_RLS_FIX.md).
The Oracle history and legacy RLS migrations are already applied to the linked
project; the commands below describe the workflow and must not be rerun blindly.

Sprint 1 uses the installed Supabase CLI migration convention. The migration filename was generated by `supabase migration new oracle_history`; `supabase init` generated the local config and ignores. `.temp` and environment files are ignored and must not be committed.

The history migration adds only `conversations`, `chat_messages`, their indexes/constraints, eight ownership policies, grants, and an invoker timestamp trigger. It does not reset, alter, or seed the existing project data. Explicit grants expose the new tables to `authenticated` only; RLS restricts rows to `auth.uid()`.

## Safety and compatibility

- Confirm the linked project matches the backend configuration before any query/migration. Never print credentials or retrieve project API keys just to inspect schema.
- Inspect catalog metadata before applying: `supabase db query --linked --file backend/database/audit_oracle_catalog_json.sql`.
- Plain CREATE intentionally fails if equivalent names already exist; inspect and adapt instead of masking a different schema with `IF NOT EXISTS`.
- `backend/database/schema.sql` contains legacy DROP/CASCADE reset statements. It is not this migration's deployment procedure.
- Existing route history and public-data policies remain separate. Sprint 1 does not silently change teammates' services or historical datasets.
- Archive conversations through the new API in Sprint 2. Owned direct DB deletion is allowed by policy and cascades only owned history, but the application need not expose hard deletion.

## Applying a reviewed migration to an existing project

```powershell
supabase db query --linked --file supabase/migrations/20261005135325_oracle_history.sql
supabase db query --linked --file backend/tests/sql/oracle_live_rls_probe.sql
supabase db advisors --linked --type all
supabase migration repair 20261005135325 --status applied --linked
supabase migration list --linked
```

The second command inserts synthetic history under two existing identities inside a transaction, verifies role/claim isolation, and rolls all rows back. It does not sign users in, modify accounts, or return personal user records. Full authenticated HTTP/browser testing still belongs to Sprints 3–6.

Apply SQL once; migration repair records an already-applied change and does not execute its SQL. An existing remote migration `20260815133157` predates this checkout's local migration directory. Preserve that history; recover/reconcile its original file before adopting a general `db push`/fresh-project bootstrap workflow. Do not fabricate a no-op replacement or mark it reverted.

## Local verification

The backend tests use existing `pytest`, `httpx`, `psycopg`, and Pydantic dependencies. Auth tests exercise the real Supabase SDK against a mocked HTTP transport. Real PostgreSQL RLS tests require an explicitly configured loopback admin database:

```powershell
$env:ORACLE_TEST_DATABASE_URL = 'host=127.0.0.1 port=55432 dbname=postgres user=oracle_test_admin'
& .\backend\.venv\Scripts\python.exe -m pytest backend/tests -q
```

The fixture refuses non-loopback hosts, creates a randomly named disposable database, installs a minimal test-only `auth.users`/`auth.uid()` stub, applies the migration, and drops that exact database afterward. Do not configure a production database for this fixture. Without the local test URL, SQL tests skip explicitly; they are not reported as passing. The minimal stub is not a Supabase Auth server.

This run used installed PostgreSQL 18 for isolated local tests and linked Supabase PostgreSQL 17.6 for live transaction verification. Docker was unavailable; no Docker install/start was attempted. Generated `supabase/config.toml` uses PostgreSQL 17 for a future full local stack; this new directory is an additive migration workflow for an existing project, not a complete recreation of the historical database.

## Rollback

Revert application code while retaining the added tables/data if rollout fails. Older code ignores the new history tables and policies, so schema contraction is unnecessary. Do not automatically DROP populated chat tables. A future authorized schema removal requires data preservation and a separate reviewed migration. No destructive rollback SQL is included.
